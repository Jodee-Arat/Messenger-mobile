Нет, полноценная архитектура Double Ratchet здесь не используется.

Фактически реализована схема:

X3DH-подобный обмен через identity key, signed prekey, optional one-time prekey;
затем один статичный sessionKey на secret chat;
сообщения шифруются через KDF(sessionKey, "MSG-KEYS") и Kuznechik;
ключ не продвигается после каждого сообщения.
1 на 1

Для DM активный путь такой:

клиент получает prekeys через backend;
если локального sessionKey нет, генерирует новый symmetric key;
передает этот sessionKey получателям через QueueSharedSecretKey, зашифрованный попарным X3DH-derived ключом;
сами сообщения дальше шифруются одним и тем же sessionKey.
Ключевые места:

apps/mobile/app/hooks/useSecretChat.actions.ts (line 1362) — генерация или загрузка activeSessionKey
apps/mobile/app/hooks/useSecretChat.actions.ts (line 1382) — DM делится sessionKey
apps/mobile/app/hooks/useSecretChat.actions.ts (line 1404) — сообщение шифруется через buildSessionMsgEnvelope
apps/mobile/app/libs/e2ee/gost.ts (line 1290) — прямо описано: после установки сессии используется простая схема без повторного X3DH
Групповые secret chats

Группа использует один общий групповой symmetric key:

инициатор генерирует groupKey;
для каждого участника строит попарный X3DH-derived ключ;
шифрует groupKey отдельно каждому участнику;
дальше все сообщения группы шифруются тем же общим groupKey.
Ключевые места:

apps/mobile/app/hooks/useSecretChat.actions.ts (line 1957) — описание групповой инициализации
apps/mobile/app/hooks/useSecretChat.actions.ts (line 2003) — генерация одного groupKey
apps/mobile/app/hooks/useSecretChat.actions.ts (line 2026) — рассылка этого ключа участникам
apps/mobile/app/hooks/useSecretChat.actions.ts (line 1710) — получение и расшифровка группового ключа
Почему это не Double Ratchet

В Double Ratchet должны быть хотя бы:

root key;
sending/receiving chain keys;
message keys;
счетчики сообщений;
обработка out-of-order/skipped keys;
DH-ratchet при смене DH public key.
В текущем коде этого нет. В Prisma/GraphQL для secret сообщений хранятся только envelope-поля: iv, encryptedMessage, sig, ukm, session ids, recipients. Нет chain/root/message-key state:

backend/prisma/schema.prisma (line 391)
backend/prisma/schema.prisma (line 446)
backend/src/core/graphql/schema.gql (line 424)
Ротация

Ротация есть, но не ratchet-ротация по сообщениям. При leave/remove backend чистит shared keys и шлет событие SECRET_KEY_ROTATION; mobile удаляет локальный my-keys.json, после чего должен получить/создать новый общий ключ:

backend/src/modules/chat/chat.resolver.ts (line 253)
backend/src/modules/chat/chat.resolver.ts (line 298)
apps/mobile/app/utils/secret-chat/secretChat.ts (line 168)
Итог

Архитектура ближе к X3DH/prekey transport + статичный symmetric session/group key, а не к Signal Double Ratchet. Компрометация сохраненного sessionKey/groupKey потенциально раскрывает сообщения этого чата за весь период действия ключа, до ручной/событийной ротации.

zero-trust(
  Нет, сейчас это не zero-trust архитектура. Есть отдельные элементы: auth guards, service-level permission checks, Redis sessions, JWT for mobile, TOTP, secret-chat E2EE-путь. Но в целом система больше похожа на обычную trusted-backend архитектуру с частичным E2EE для secret chats.

Главные причины

Realtime/subscriptions часто доверяют client-supplied userId
Много подписок без @Authorization() и без сравнения variables.userId с authenticated user. Например:
chat.resolver.ts (line 140), message.resolver.ts (line 38), group.resolver.ts (line 109), friendship.resolver.ts (line 164).

Secret subscriptions сделаны лучше: там есть @Authorization() и проверка authenticated user:
secret.resolver.ts (line 284).

Auth модель раздвоена
Web использует cookie/session, mobile использует JWT + refresh + x-session-id. Access token живет 15d, refresh token фактически stateless и без серверной ротации/denylist:
session.service.ts (line 175).

Secret chats не дают полноценный zero-trust
Сервер не видит plaintext secret messages, это плюс. Но ключи статичные на чат/группу, нет Double Ratchet/MLS, локальные ключи и сообщения лежат в document/AsyncStorage-подобных местах, Android backup включен:
secretChat.ts (line 232),
AndroidManifest.xml (line 14).

Обычные чаты и файлы полностью доверяют backend
Обычные сообщения plaintext на сервере. Файлы выдаются через presigned URL. Есть конкретный риск: downloadFile проверяет доступ к chatId, но не проверяет, что fileId принадлежит этому chatId:
file.service.ts (line 194).

Секреты/config hygiene слабые
В репозитории есть .env файлы. Даже без раскрытия значений это несовместимо с mature zero-trust/least-secret-exposure подходом.

Что сделать, чтобы стало похоже на zero-trust

Закрыть subscriptions
Все подписки должны быть @Authorization(). Убрать доверие к userId из args: брать user id только из GraphQL context. Для chatId/groupId проверять membership на subscribe и/или на каждом событии.

Унифицировать auth
Короткий access token, например 5-15 минут. Refresh tokens хранить/ротировать сервер-side, привязывать к device/session id, уметь отзывать. Web/mobile должны идти через один понятный session/device model.

Ввести resource-scoped authorization в сервисах
Каждый fileId/messageId/chatId/groupId/roleId должен проверяться как связанный ресурс. Исправить downloadFile: искать файл по { id: fileId, chatId }.

Перевести secret-chat к настоящей крипто-архитектуре
Для 1:1: X3DH + Double Ratchet.
Для групп: MLS или Sender Keys-подобная схема.
Не кастомизировать протокол без крипторевью.

Укрепить local-at-rest
Secret keys/messages хранить в secure/encrypted storage, отключить backup для sensitive data, разделить кэш вложений и ключевой материал.

Разделить trust levels продукта
Явно: обычные чаты = trusted backend. Secret chats = server-untrusted content. Сейчас это смешано в одном приложении без полноценной boundary-модели.

Добавить abuse/security tests
Тесты на: чужой userId в subscription, чужой chatId, чужой fileId, revoked session, removed member после key rotation, stale JWT/refresh.

Итог

Проект имеет security-oriented элементы, но zero-trust пока только частично и местами. Самый быстрый путь приблизиться: сначала закрыть subscriptions и resource authorization, затем унифицировать auth/session model, потом отдельно довести secret-chat crypto/storage до уровня настоящего E2EE-протокола.
